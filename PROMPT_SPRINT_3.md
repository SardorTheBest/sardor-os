# Промпт: Sprint 3 — интерактивный календарь для Zenith Personal OS

Ты — опытный frontend-инженер. Продолжи разработку **Zenith Personal OS** и реализуй интерактивный модуль календаря в стиле Google Calendar. Работай с существующей архитектурой проекта, не ломай текущий функционал и не добавляй тяжёлые UI-библиотеки.

## 1. Сначала изучи текущий проект

Перед написанием кода проанализируй существующие файлы, особенно `StorageManager`, `TagManager`, `ToDoModule`, точку входа приложения и глобальные стили. Учитывай фактический стек и паттерны проекта:

| Область | Обязательное требование |
| --- | --- |
| Хранение данных | Все операции с задачами и тегами выполняй через `StorageManager`; не обращайся к `localStorage` напрямую из UI-модуля. |
| Задача | Используй модель: `id`, `title`, `description`, `isCompleted`, `dueDate`, `dueTime`, `tagId`, `createdAt`, `updatedAt`, `isSynced`. |
| Тег | Используй модель: `id`, `name`, `color`, `updatedAt`, `isSynced`. |
| Дата и время | Сохраняй дату в формате `YYYY-MM-DD`, время — в формате `HH:MM`. |
| Совместимость | Не меняй публичные контракты существующих модулей. Если `TagManager`, `ToDoModule` или `main.js` имеют другие имена либо проект использует React/TypeScript, адаптируй интеграцию к реальной структуре и явно объясни замену в инструкции. |

## 2. Цель спринта

Создай полностью рабочий `CalendarModule.js` и подключи его к существующему приложению. Модуль должен отображать задачи с заполненными `dueDate` и `dueTime`, давать пользователю возможность перемещаться по календарю и взаимодействовать с задачами и тегами.

Не используй сокращённый, псевдокодовый или демонстрационный вариант. Выдай полный код всех изменённых файлов и точные инструкции по подключению.

## 3. Обязательная функциональность календаря

### 3.1. Месячная сетка

Реализуй алгоритм построения календарной сетки для любого месяца и года.

1. Всегда отображай заголовки дней недели в порядке: **Пн, Вт, Ср, Чт, Пт, Сб, Вс**.
2. Корректно вычисляй количество дней текущего месяца, день недели первого числа и ячейки соседних месяцев, необходимые для заполнения сетки.
3. Отображай дни предыдущего и следующего месяца в тех же ячейках сетки, но приглушённым цветом и/или пониженной прозрачностью.
4. Выделяй текущую календарную дату заметным, контрастным контуром либо акцентным фоном.
5. Обеспечь устойчивую работу на переходах через декабрь–январь, в високосные годы и при первом дне месяца в воскресенье.

### 3.2. Навигация и режимы просмотра

Добавь панель управления календарём со следующими элементами:

1. Кнопка `<` для перехода к предыдущему месяцу.
2. Кнопка `>` для перехода к следующему месяцу.
3. Кнопка **«Сегодня»**, возвращающая календарь к текущему месяцу и текущей дате.
4. Текстовый индикатор открытого периода в локали `ru-RU`, например **«Август 2026»**.
5. Переключатель режимов **«Месяц / Неделя / День»**. Полноценно реализуй месячный режим. Для недели и дня создай доступные интерактивные состояния и подготовь архитектуру/обработчики к их расширению; не выдавай неработающие элементы за готовую функциональность.

### 3.3. Отображение задач

Для каждой задачи из `StorageManager`, у которой одновременно заполнены `dueDate` и `dueTime`, выведи плашку в ячейке соответствующей даты.

1. Сортируй плашки внутри дня по `dueTime` по возрастанию.
2. Каждая плашка должна включать время, например `14:00`, и краткое название задачи.
3. Цвет плашки должен соответствовать `color` привязанного тега из `TagManager` или хранилища тегов. Если тег отсутствует или `tagId` пустой, используй нейтральный безопасный цвет из токенов интерфейса.
4. Если в одном дне больше трёх задач, показывай первые три, затем интерактивную кнопку **«+ X ещё»**. По нажатию раскрой скрытые задачи в понятном, доступном интерфейсе.
5. Задачи соседних месяцев должны показываться в их соответствующих ячейках, но не должны ухудшать визуальную иерархию основного месяца.

### 3.4. Взаимодействия

Реализуй следующие сценарии:

1. Клик по пустому месту ячейки дня открывает создание задачи в `ToDoModule` с автоматически подставленной датой выбранного дня.
2. Клик по плашке задачи открывает просмотр или редактирование этой задачи в `ToDoModule` по её `id`.
3. Предотврати конфликт клика по плашке и клика по ячейке: открытие задачи не должно запускать создание новой задачи.
4. После создания, изменения или удаления задачи календарь должен обновляться без перезагрузки страницы. Используй подписку/событие хранилища, если оно доступно.
5. Создай модальное управление тегами, в котором можно выбрать цвет категории через нативный `<input type="color">` и сохранить изменение через `StorageManager`/`TagManager`.
6. Все кнопки и интерактивные элементы должны быть доступны с клавиатуры, иметь различимые состояния `:hover`, `:active` и `:focus-visible`, а модальные окна — корректное закрытие по Escape и возврат фокуса к триггеру.

## 4. Единый визуальный стиль

Используй или добавь следующие CSS-токены **без изменения указанных HEX-значений**:

```css
:root {
  /* Цветовая палитра */
  --bg-main: #0f0f11;
  --bg-card: #18181c;
  --bg-card-hover: #222228;
  --bg-accent-card: #1b2332;

  /* Границы и разделители */
  --border-color: #242429;
  --border-radius-sm: 8px;
  --border-radius-md: 12px;
  --border-radius-lg: 16px;

  /* Текст */
  --text-primary: #fffffe;
  --text-secondary: #a0a0a8;
  --text-muted: #62626a;

  /* Акценты */
  --accent-cyan: #00e5ff;
  --accent-mint: #00ffab;
  --accent-gold: #e5a93c;

  /* Шрифты */
  --font-main: 'Inter', system-ui, -apple-system, sans-serif;
  --font-mono: 'JetBrains Mono', monospace;
}
```

Оформи интерфейс в эстетике **Minimalistic Dark / Zen Minimal**: чистый контраст, сдержанные карточки на `--bg-card`, аккуратная сетка, крупные заголовки и моноширинные цифры/время. Не используй градиентные плашки, избыточные тени и визуальный шум. Шаг отступов — только кратный **8 px**: преимущественно `8 px`, `16 px`, `24 px`.

Добавь переходы длительностью около `0.2s ease` и учитывай `prefers-reduced-motion`. Интерфейс должен быть адаптивным: на мобильном устройстве сетка и панель управления не должны требовать горизонтальной прокрутки.

## 6. Технические ограничения

1. Используй только чистый CSS, Flexbox и CSS Grid. Не подключай тяжёлые UI-библиотеки и не переписывай базовые стили сторонними фреймворками.
2. Разделяй интерфейс на переиспользуемые компоненты/модули: `Card`, `Button`, `ProgressBar`, `Badge`, `Modal` — только если это соответствует фактической архитектуре репозитория.
3. Не меняй заданные HEX-коды и не дублируй бизнес-логику хранения данных в UI.
4. Не добавляй вымышленные задачи, теги, отзывы или данные. Используй реальные записи хранилища и корректные empty states.
5. Обработай некорректные/неполные данные безопасно: задача без даты и времени не должна ломать календарь и не должна отображаться как запланированная.
6. Добавь минимум один smoke-тест или небольшой проверяемый сценарий для ключевых функций: вычисление дней месяца, сортировка задач и обновление представления после изменения данных.
